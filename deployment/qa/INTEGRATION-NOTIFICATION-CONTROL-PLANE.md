# Integration and notification control plane audit

The operator surface is **Delnavazan Settings → Integrations**. Email, Meta WhatsApp Cloud API, SMS fallback, and Google OAuth/Calendar each have a save/update screen and explicit local readiness check. The buttons do not send test traffic, messages, or Google API requests.

## Routes, events, and operational evidence

- Stripe inbound webhook: `delnavazan-platform/v1/payment-provider-events/{provider}[/{account}]`. Requests are signature-verified and receipted, with test-mode account/secret requirements enforced by payment execution.
- Google OAuth uses authenticated `admin-post.php` actions `dzn_google_connect`, `dzn_google_oauth_callback`, and `dzn_google_disconnect`. Calendar projection is performed by `dzn_google_calendar_projection_dispatch`; it is not a webhook.
- General notification intents are the closed `NotificationRule::INTENTS` set: automatic renewal upcoming/charged/failed, manual renewal payment required, guarantee deadline approaching/expired, payment failed/recovered, term lapsed, refund review required/resolved. `GUARANTEE_EXPIRED` has no producer and is explicitly unbound.
- Teacher invitations use the separate `dzn_teacher_invitation_delivery_dispatch` worker because the one-time invitation secret is created only at that transport boundary.
- Existing communications diagnostics report queue backlog, leases, retry exhaustion, unregistered/unroutable intents and notification state counts. The new Integrations page adds mail handoff readiness, invitation outbox counts, notification runtime/channel configuration and Google OAuth client presence. Both are read-only and capability-gated.

## Security and remaining human decisions

- Secrets are never rendered back by settings. Email, Meta, SMS, and administrator Google OAuth secrets use AES-256-GCM authenticated encryption bound to provider/field with WordPress secure salts; teacher OAuth tokens continue using the provider credential vault. Stripe credentials use the payment secret vault. Never commit provider credentials.
- Email/SMTP vendor and the deployment location for mail credentials must be chosen by the operator/hosting owner. Once selected, provide that mail transport as the existing deployment binding and verify teacher invitations on staging.
- Decide whether any of the notification intents should be active for launch, then approve copy, audience, channel, locale and fallback behavior.
- Decide whether WhatsApp or SMS is required and select the provider/product, consent and sender policy, credentials owner, webhook/delivery receipt contract and spend constraints. Until then both remain unconfigured.
- Confirm whether Google Calendar/Meet is required at launch; if yes, create/configure the OAuth client and callback, supply deployment constants, and complete an authorised staging connection/projection check.
- Supply Stripe **test-mode only** credentials and an authorised staging test window if checkout is a launch requirement. Keep production activation disabled.
- A “test connection” cannot be safely inferred for mail, Google, WhatsApp, SMS or Stripe from local presence checks. External validation requires the above decisions and explicit non-production credentials/runtime activity, none of which this issue performs.
